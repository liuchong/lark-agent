# Bounded Convergence And Partial Results

## Goal

Prevent a useful bounded investigation from collapsing into repeated full model
runs and a generic failure notice.

The accepted behavior has six outcomes:

1. a fully supported answer remains the preferred terminal result;
2. a bounded investigation that proves only part of the answer returns a
   clearly limited partial result instead of being discarded;
3. missing or ambiguous input produces an exact clarification request without
   forcing irrelevant code reads;
4. a reply that passed content and evidence validation is persisted before the
   final owner-handled check and is never regenerated solely because that check
   is temporarily ambiguous;
5. deterministic model-output failures are repaired or safely downgraded in the
   current run, while only genuinely transient provider failures use the
   general retry budget;
6. terminal owner notices report the safe draft or successful completed checks,
   the exact candidate unknowns when available, otherwise the unresolved
   original result, final blocker, and next action instead of only saying that
   bounded retries stopped.

## Research Basis

The Chinese and English v1.3 editions of *AI Agents in Depth* treat the harness
as the combination of context, tools, constraints, validation, and correction,
and distinguish retryable failures from permanent failures and no-progress
loops. The local Kimi Code/CLI, Codex, and OpenCode references use the same
externally verifiable pattern: model-visible status is guidance, while the host
runtime owns hard budgets, tool-error feedback, checkpoints, and repeated-call
termination. Public Claude Code and Cursor material supports extensible rules,
skills/hooks, bounded loops, checkpoints, and evaluation, but does not expose
their private terminal algorithms. This change therefore reuses those
testable patterns without copying reference code or claiming undocumented
internals.

## Business Design

### Reply Outcome And Progress

`Decision` gains an outcome independent from `evidence_status`:

- `complete`: every concrete requested claim is supported at the evidence level
  required by the current work kind;
- `partial`: bounded work produced one or more useful facts or a proven
  investigation limit, but one or more requested facts remain unknown;
- `clarification`: the exact missing input or ambiguous referent prevents a
  safe investigation or answer.

Reply decisions also carry structured progress:

- `completed_checks`: bounded checks backed by current-run receipts;
- `initial_finding`: the safe result that can be stated now;
- `unknowns`: unresolved facts without unsupported inference;
- `next_step`: one concrete action the sender or Owner can take.

`evidence_status` remains the trust boundary for code claims. A `complete`
coding answer normally requires `verified`. A `partial` answer may contain
verified claims plus explicit unknowns or may be `insufficient` when the only
safe result is that the configured workspace, path, or symbol could not be
verified. `clarification` never turns missing input into a code fact and does
not require a successful code read.

The runtime validates progress against receipts. A model statement that it
read, searched, tested, or verified something without the matching current-run
receipt is still rejected.

### Prompt Layers

The model-visible contract is split into three layers:

1. a stable core contains identity, authority order, Lark and Workspace safety,
   untrusted-tool-data handling, and the rule that only the Go runtime performs
   external sends;
2. a task process describes the current work kind as a short executable flow:
   understand, choose direct/clarify/investigate, plan if required, gather the
   minimum evidence, classify claims, and submit a typed outcome;
3. a dynamic run-state reminder contains remaining turn/tool/context budgets,
   successful completed tool names, typed unknowns, the last failed gate, and
   the currently legal terminal outcomes. Repeated-result prompts include the
   matching fingerprint count and required disposition.

Dynamic state is generated by Go before every model request and after
compaction. The model does not infer counters or completed work by scanning old
chat text. Prompt restrictions never replace path, permission, evidence,
budget, or send enforcement in Go.

Terminal-only repair instructions include the last rejection reason, reusable
evidence, legal downgrade choices, and the exact action that must not be
repeated. `partial` and `clarification` are ordinary terminal outcomes, not
evidence bypasses.

### Investigation State And Failure Disposition

The current run maintains compact state outside the model transcript:

- successful receipt digests and allowed/authoritative sources;
- completed successful tool names and current-run code-read count;
- typed unknowns from the submitted decision and the last terminal rejection.

Raw model and tool events remain in `agent_steps`. Dynamic prompts receive only
the bounded state needed for correction; durable terminal summaries derive
tool names from successful recorded steps and do not copy rejected prose.

Runtime failure paths converge to one observable handling outcome:

- `retry_transient`: retry after a provider/network delay;
- `retry_with_changed_input`: the next call must change arguments or evidence
  source;
- `converge_partial`: preserve supported facts and submit explicit unknowns;
- `ask_clarification`: request the exact missing input;
- `hold_for_context`: preserve a safe candidate and recheck the conversation;
- `stop_unsafe`: do not expose an unsupported or result-uncertain action.

A tool-result fingerprint binds tool name, normalized arguments, success/error
class, and a bounded result digest. The second identical occurrence receives an
actionable strategy-change result. With the default ceiling, the third
identical occurrence closes broad investigation and exposes only
`submit_decision`. An unchanged deterministic failure never starts another
full work-item model run.

Current evidence and grounding validators are deterministic runtime gates.
Their actionable rejection stays inside the current run.

### Safe Reply Candidate

Schema version 16 adds `work_reply_candidates`. One work item may have one
active candidate. The durable record contains:

- work item ID and decision JSON;
- decision digest;
- status `pending`, `held`, `consumed`, or `cancelled`;
- hold or cancellation reason;
- created and updated timestamps.

Only a Decision that has passed language, identity, permission, quality, and
evidence validation may become a candidate. Rejected free-form drafts remain
audit steps and are never copied into a sender-facing or Owner-facing message.
Candidate creation and every pending/held transition require the exact current
processing lease; an expired worker cannot create, replace, hold, consume, or
cancel a candidate.

The candidate is saved before the final owner-handled check:

- `unanswered`: complete the existing delegated Owner notice, send the exact
  candidate once through the normal idempotent reply action, then consume it;
- `answered`, `no_reply_needed`, or `withdrawn`: cancel it and complete without
  a sender-facing message;
- `ambiguous`: hold it and defer only the semantic check.

When held work is claimed again, the daemon first reapplies the current routing
policy, then resolves owner handling without calling the main model. A policy
change that pauses or blocks the work cancels the old candidate. A process
restart retains the candidate. Explicit `/task resume <id> confirm` or forced
CLI resume means "investigate again": it cancels the old candidate and resets
the new terminal generation.

### Retry Budgets

`policy.owner_reply_max_retries` defaults to 3. It limits initial and final
owner-handled semantic rechecks. The existing `policy.owner_reply_retry`
controls their interval.

`agent.max_retries` remains the ceiling for transient provider, rate-limit, and
network failures. Deterministic schema, quality, grounding, evidence, policy,
no-progress, and verifier results do not consume that general budget by
rerunning the whole investigation. SQLite stores semantic deferrals in
`owner_reply_retry_count` and provider failures in `retry_count`. Migration
from schema v15 moves retries on active `waiting_user` rows into the semantic
counter so neither budget is silently reset or double-counted.

At the semantic ceiling, the work enters dead letter atomically. The Owner
notice includes the unsent candidate when one exists, completed checks, exact
unknowns, final hold reason, and `/task` inspection/resume commands. The
original sender receives no late message.

### Permission, Identity, And Idempotency

This change does not broaden tool authority or reply scope:

- a non-owner-triggered run remains read-only and same-chat scoped;
- Workspace paths remain code-enforced inside the configured real root;
- Lark production calls remain under `internal/lark` and the official Go SDK;
- the delegated Owner notice still completes before the sender-facing reply;
- candidates are internal state, not external actions, and do not replace
  durable reply-action idempotency;
- result-uncertain external actions are never replayed.

### Evaluation Harness

An offline fixed-scenario harness runs synthetic cases with scripted model
behaviors and exact call ceilings:

- preserves useful structured partial progress without fixed wording;
- asks for clarification without a fake code read;
- repeats the same tool and arguments;
- insists on an unsupported code assertion;
- converges after the runtime rejects that unsupported assertion.

The catalog validates a typed outcome and declared model/tool ceilings for each
scenario. Executable cases assert the resulting outcome and the call bound
relevant to the behavior under test.
Candidate persistence, semantic resolver sequences, duplicate sends, schema
migration, and terminal Owner notices remain integration tests outside this
focused model-loop harness and run under `make verify`.

`make harness-eval` is deterministic and requires no network or secret. An
explicit optional live-model run may reuse the existing OpenAI-compatible
configuration one model at a time; it is never part of `make verify` and never
stores credentials or real Lark messages.

### Configuration And Installation

The generated configuration and documentation add:

```yaml
policy:
  owner_reply_max_retries: 3
```

The install paths, Keychain contract, LaunchAgent label, SDK boundary, and
secret handling do not change. Installation occurs only after validation and
commit.

### Fixtures

All fixtures use synthetic chat IDs, message IDs, source paths, source text,
owner names, and model responses. The storage test constructs a synthetic v15
SQLite state in a temporary directory for migration coverage. Real failed work
items inform scenario shapes only and are never copied into the repository.

## BDD Acceptance

### Scenario: Partial coding conclusion

Given a coding run has a current authoritative read that proves one requested
fact but cannot prove another, when bounded repair cannot complete the second
fact, then it returns `partial`, cites only supported claims, names the exact
unknown, and does not rerun the full investigation.

### Scenario: Missing input clarification

Given the current message is unreadable or lacks the path, code, attachment, or
referent required to investigate, when the task was previously classified as
coding work, then `clarification` completes without a fake code read or generic
failure notice, and the runtime replaces free-form code claims with a
deterministic request framed only as unknowns and the required next input.

### Scenario: Held candidate becomes answerable

Given a validated delegated reply candidate and an ambiguous final owner check,
when the next semantic check becomes `unanswered`, then the main model ran once,
the exact candidate survived the defer, and the sender receives it once after
the Owner notice.

### Scenario: Held candidate is no longer needed

Given a held candidate, when a later semantic check finds the Owner answered or
the source message was withdrawn, then the candidate is cancelled and no
sender-facing reply is sent.

### Scenario: Semantic retry ceiling

Given the final owner check remains ambiguous for three attempts, when the last
exact lease is deferred, then the work enters dead letter, the original chat
receives no message, and the Owner notice says the draft was not sent and
contains the candidate or safe progress, unknowns, next step, and `/task`
commands.

### Scenario: Repeated deterministic failure

Given a model repeats the same tool arguments and receives the same error
class, when the condition does not change, then the harness asks for a changed
strategy, narrows investigation, and finally exposes only
`submit_decision`; it never converts the repetition into 20 full model runs.

### Scenario: Unsupported candidate remains private

Given a draft contains a path or identifier absent from its authoritative
reads, when targeted correction still fails, then the draft never becomes a
candidate and is not sent to the original chat; the Owner sees only a
deterministic safe progress summary.

### Scenario: Prompt is not the safety boundary

Given a scripted model ignores the process prompt and attempts a forbidden
tool, unsupported reply, or over-budget investigation, when the call reaches
the Go harness, then the deterministic policy rejects it and the run converges
to a safe typed outcome.

### Scenario: Retry and lease counters remain independent

Given the provider retry ceiling is lower than the semantic context ceiling,
when a semantic defer occurs, then only `owner_reply_retry_count` advances.
Given an expired worker tries to save a candidate, then its stale lease is
rejected and cannot overwrite the current run.

### Scenario: Resume and migration

Given a v15 database, a candidate saved before a crash, duplicate intake, or an
explicit terminal resume, when v16 migration and recovery run, then candidate
state, reply idempotency, cancellation, and terminal-generation behavior match
this design without replaying an external action.

## Non-Goals

- no automatic late reply for already dead-lettered historical work;
- no weaker production-source or grounding requirement;
- no second send channel, browser automation, or `lark-cli` production process;
- no copied reference-project code or new external dependency;
- no generic hook marketplace, Ralph-style outer loop, full event-sourcing
  rewrite, multi-agent debate, model fine-tuning, or LLM compaction for the
  foreground IM path;
- no live-model evaluation in default verification.

## Reserved Interfaces

No unfinished user-visible command or half-enabled feature is reserved. Future
LLM compaction, multi-model grading, or generalized hooks require independent
specification and acceptance before exposure.

## Completion And Stop Conditions

The task is complete when the long-term specification, migration, runtime,
commands, documentation, help text, deterministic harness, focused tests, full
verification, independent review, commit, installed daemon, and feasible live
Lark acceptance all agree with this behavior. Findings unrelated to safe
partial delivery, bounded convergence, identity, evidence, persistence, or
idempotency are recorded for later rather than expanding this change.
